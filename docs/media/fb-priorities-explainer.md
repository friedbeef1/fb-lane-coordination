# FB explainer — What should happen next?

Status: script and storyboard candidate, not a rendered video.
Audience: hands-on product managers and founders using Codex across several
conversations. Target: 100–115 seconds, landscape 16:9, captioned, legible on a
phone. Suggested production: Hyperframes, original diagram/card animation;
no private conversations, customer data, invented testimonials or savings.

## Script and storyboard

Before means **without FB Lanes**; after means **with FB Lanes**. Use the same
illustrative project, person, model and inputs on both sides. This is not a
comparison of old and new FB, nor a measured performance demonstration.

| Time | Narration | On-screen visual |
|---|---|---|
| 0–16s | Without FB Lanes, you can already have deep, ongoing conversations with Codex: debate design, investigate technical constraints, explore the market. Ask follow-ups. Challenge answers. Keep thinking even when nothing is being built. | Persistent label “Without FB Lanes.” Three chats each show several exchanges; investigation overlaps. Show competent, useful outputs, not artificial chaos. |
| 16–32s | But good conversations don't automatically give you the combined picture. What was actually decided? Does that Design recommendation depend on blocked Tech work? Which request goes first? These questions still need answers across the chats. | Same useful chat outputs. Label “Without FB Lanes — no shared coordination process.” Highlight a Design proposal beside a separate blocked Tech prerequisite. PM question cards: “Decided?” “Blocked?” “First?” No invented code failure. |
| 32–48s | With FB Lanes, keep the deep conversations. Handoffs separate actionable decisions, evidence and open questions. A recommendation waits for Product/BFM intake; sending it does not start a build while you're still exploring. | Replay the same inputs under “With FB Lanes.” Decisions and assumptions labelled separately; open question stays in chat. Notification: “Noted. No work started.” Resolve the “Decided?” card. |
| 48–64s | Invoke BFM in Product. It reconciles recorded recommendations and dependencies, then explains what goes first, what's blocked and what should wait—with reasons. You can change the proposed plan before execution. | Connect the Design recommendation to its Tech prerequisite. Resolve “Blocked?” with owner/action and “First?” with explained sequence. Show deferred item, not a disappearing card. |
| 64–86s | Now the CEO needs something delivered first. What gets pushed back? Is something it depends on still blocked? FB makes those implications clear: what must happen first, which work would wait, and what can safely continue. | Paired problem/response: “Without FB Lanes” shows an urgent request plus unanswered impact questions; “With FB Lanes” shows “Must happen first,” “Proposed for later,” and “Can continue,” with reasons. Label “Illustrative example,” not measured result. Neither side bypasses required approvals. |
| 86–102s | Later, you reopen Design. What happened to its recommendation? FB's result-return process brings back the outcome and evidence—or reports that delivery is pending. Your next deep conversation has a concrete result to examine. | Before: original recommendation, outcome not recorded there. After: implemented / blocked / deferred outcome with link and next action. Add Ready to ship → Push Live as a separate release boundary. |
| 102–115s | Codex can do these coordination tasks when instructed. FB makes them a consistent process. Not better conversations by magic—less confusion about how their conclusions become coordinated work. | Closing pair: “Which decisions? What goes first? What happened?” → “Connected conclusions. Explained priorities. Returned outcomes.” Repository link and optional `$fb-setup` CTA. |

## Production notes

- Give ongoing conversations the opening third of the film, not a passing mention.
- Keep “Without FB Lanes” and “With FB Lanes” labels explicit throughout the comparison.
- Each comparison beat must show a PM uncertainty first, then the matching FB response—not two lists of features.
- The illustrative before case has no shared coordination process; it is not evidence that every non-FB workflow has these problems.
- Never portray vanilla as incapable of planning, coordination or safety; show the difference in supplied conventions.
- Show repeated questions and revisions in the same chats, not six instant answers.
- Then connect selected conclusions to a changing queue with reasons.
- Do not imply unlimited chat memory, transcript capture or automatic chat access.
- Graph relationships appear only when explaining a prerequisite or impact.
- Use 3–4 short labels at a time; distinguish priority from execution order.
- Use captions plus optional narration; do not depend on audio to explain gates.
- No speed, token, revenue, adoption or guaranteed-error-prevention claims.
- No simulated UI presented as a live Codex screen. Label diagram examples.
- Reuse the old demo only as historical reference, not current product footage.
- Before rendering, validate narration against the shipped candidate, choose
  voice/music assets with permission, and review actual frames for readability.
- The current plugin is Codex-only. Do not imply native Claude installation.
